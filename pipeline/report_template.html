Calidad de datos

Los controles bloqueantes protegen el modelo (grano, nulos, valores imposibles): si uno falla, no se publica. Los avisos miden anomalías del dato público; se cuentan y se publican.

Cómo reproducir

Con uv instalado, desde la raíz del repositorio. Cada paso es idempotente: una corrida sin cambios en el origen no modifica nada.

# dependencias
uv sync
# toda la cadena con tiempos: build, costo, robustez, wiki, este tablero, repetición y verificación de cifras
uv run python -m pipeline.run_all
# agrega la descarga desde la Secretaría (hace falta salida a su servidor)
uv run python -m pipeline.run_all --with-ingest
# tests, incluida la reproducibilidad de este archivo
uv run pytest -q

Para recorrer los resultados sin correr nada: repetición temporal (mapa de pozos mes a mes) y wiki de hallazgos (wiki/index.md, con el libro de hallazgos, la robustez del eje y la interferencia).

Cómo está hecho

  1. Ingesta (pipeline/ingest.py): GET condicional (ETag / Last-Modified), hash SHA-256 y capa raw inmutable con un archivo por versión. Una corrida sin cambios no escribe nada.
  2. Modelo (pipeline/sql/, DuckDB): staging tipado, normalización de razones sociales (seeds/operadores.csv), hechos con grano (pozo, mes), dimensiones de pozo y fractura, marts para el reporte. Todo se reconstruye desde raw: idempotente.
  3. Calidad (pipeline/checks.py): controles bloqueantes y avisos con conteo y muestra; el reporte JSON queda versionado.
  4. Interferencia (pipeline/sql/04_interferencia.sql): pads por coordenadas de superficie, pares padre/hijo a menos de 5 km, estudio de eventos con control de igual edad.
  5. Preguntas en lenguaje natural (agente/): un modelo de lenguaje (local por defecto) elige una de 16 operaciones tipadas y completa sus argumentos; nunca escribe SQL ni números. Las mismas operaciones se exponen como servidor MCP de solo lectura.
  6. Publicación: ./refresh.sh (semanal, desde una máquina en Argentina) corre tests, ingesta, build y este sitio. GitHub Actions corre los tests en cada push.
